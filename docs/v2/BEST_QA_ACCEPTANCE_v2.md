# B.E.S.T. Academy — план качества и критерии приёмки v2

Статус: будущие проверки и gates. Они не объявляются выполненными. Уже выполненные диагностические проверки legacy описаны отдельно ниже. [Roadmap](BEST_ROADMAP_v2.md), [решения](BEST_DECISION_REGISTER_v2.md).

## Разделение видов готовности

1. Проект принят: документы/прототипы согласованы, открытые решения видны.
2. Функция реализована: код и meaningful tests существуют, ограничения описаны.
3. Интеграция проверена: реальная операция в test Telegram/Google/хостинге дала ожидаемый результат.
4. Методическая приёмка: автор/проверяющий подтвердил содержание и безопасность соответствующей версии/локали.
5. Релиз/пилот принят: выполнены все нужные gates, backup/restore, роли и пользовательский маршрут.

Ни одна ступень не следует автоматически из предыдущей. Успешный build, открытый порт или создаваемый PNG не заменяют функциональный тест. Имитация API не равна внешней интеграции. Число тестов само по себе не доказывает покрытие требований.

## Тестовая стратегия

| Уровень | Что должно реально проверяться | Среда |
|---|---|---|
| Unit | Policy, расчёт баллов/компетенций, critical, prerequisites, transitions, роли/назначения | Быстрые чистые функции с принятыми fixtures |
| Content/schema | Поля, ID/версии, 4 локали, ссылки, prerequisites DAG, rights/alt/review, case completeness | Все импортированные записи; статус draft отдельно от valid/published |
| API integration | Транзакции, auth/RBAC/object access, ревизии, идемпотентность, outbox | Реальная PostgreSQL, тестовые аккаунты |
| Migration | Пустая и предыдущая схема, сохранность rows/FK, повтор импорта и restore | PostgreSQL; отдельный SQLite smoke при поддержке |
| Telegram | Настоящие routers/filters/FSM, Message/CallbackQuery, ошибочные/устаревшие действия | Локальная recording session + выделенный test bot для внешнего шага |
| Browser E2E | Вход, урок, checkpoint, интерактив, назначения, результат, отказ чужому профилю | Playwright + поднятые API/БД, контролируемые данные |
| Mobile/Mini App | Реальные viewport/WebView, initData, cookies/token behavior, возврат/повторное открытие | Браузер и реальные Telegram-клиенты целевой матрицы |
| Accessibility | Keyboard, focus, контраст, screen-reader labels, reflow, reduced motion | Автоматика + ручная проверка |
| Method/safety | Смысл, ключи, техника, контекст, переводы и ограничения | Автор/уполномоченный специалист; не тестовый assert |
| Operations | Реальный restart, cold start, backup/restore, отказ зависимостей | Выбранная test площадка без production-секретов |

## Обязательные контрольные сценарии

### Identity и доступ

- Разные учётные записи для ученика, родителя, инструктора, экзаменатора, редактора и администратора; попытка ученика вызвать studio API завершается отказом.
- Инструктор A не читает/изменяет ученика B вне назначенного scope, включая прямой запрос по UUID и экспорт. Срок/отзыв назначения действует сразу по серверной policy.
- Независимый браузерный вход работает без Telegram. Связь Telegram с аккаунтом требует обеих проверок, чужой username не позволяет перехват.
- Неверное/старое/модифицированное initData отвергается; повтор обмена не создаёт чужую сессию; bot token не попадает в bundle, URL, логи и ответы.
- Ограничение входов, CSRF, истечение/отзыв сессии, одноразовые приглашения и recovery tested. Профиль ребёнка не появляется в публичном поиске; нет открытых контактов.

### Учебный маршрут и контент

- Все 15 обязательных блоков Balance доступны и соответствуют опубликованной версии. Перезагрузка/выход/рестарт возвращают checkpoint, а не случайный урок.
- SVG управляется мышью, сенсором и клавиатурой; есть текстовая альтернатива. Обозначение учебного упрощения видно; схема не выдаёт оценку реального навыка.
- Только прошедшая необходимые approvals версия публикуется. Попытка опубликовать без safety/rights/перевода завершается отказом; изменение источника не наследует approvals новой версии.
- Изменение published-вопроса создаёт новую версию. Старые результаты открывают старый snapshot. Отозванный материал перестаёт предлагаться для новых занятий с понятным объяснением.
- Все legacy records присутствуют в staging, duplicate occurrence mapping сохранён; флаг «не принят» не выдаётся за удалённый вопрос. Ни `access.codes`, ни service-account JSON не оказываются в новой публичной выгрузке.

### Экзамен

- Все граничные значения выбранной policy: ниже/ровно/выше каждого порога; score, max_score и percent отображаются отдельно.
- Critical-ошибка имеет утверждённое действие в начале, середине и конце; пропуск critical не позволяет получить положительный квалификационный итог.
- Неполная попытка, досрочный submit, клиентский поддельный score, старый порядок вариантов, неверный тип ответа и чужой attempt ID не дают недопустимый результат.
- Перемешивание сохраняет правильный ключ через option IDs; связанные кейсы имеют контекст и порядок. Повторный submit/Update не создаёт второго балла, результата или сертификата.
- Перезапуск после создания, сохранения ответа и submit восстанавливает те же вопросы/порядок/время/результат. Проверка ведётся на нескольких пользователях с разными попытками.
- Серверный deadline не продлевается сменой часов/языка/`/start`; политика паузы и пересдачи проверяется управляемым временем без реального ожидания 30 дней.
- Параллельные ответы и ответ одновременно с submit не нарушают invariant; протестировать обе последовательности и конфликт revision.

### Практика и документы

- Практический результат вводит только уполномоченный назначенный экзаменатор по опубликованной рубрике; истёкшие полномочия не подходят.
- Теория без обязательной практики не порождает итоговый статус. Отозванное основание не остаётся молча действующим.
- Кириллица, длинные имена, разные локали, число/версия документа и читаемость визуально проверены. Шрифт с лицензией действительно поставляется, fallback не маскирует квадраты.
- Номер уникален, повтор выдачи идемпотентен, отзыв/замена видны в проверке. Публичный ответ содержит только утверждённые поля; детский профиль не раскрывается.

### Интеграции и эксплуатация

- После успешного commit результата недоступность Sheets/Telegram не стирает данные. Retry outbox не дублирует внешнюю строку/выдачу; receipt проверяется.
- Ошибка БД до commit не показывает ложное «сохранено». Зависший worker восстанавливается по lease; устаревшее задание не выполняется бесконтрольно.
- Test bot действительно отвечает `/start`, проходит роли, восстановление, меню и весь опубликованный тест. Callback всегда подтверждён; старое меню безопасно отклоняется; полезная история не удаляется.
- Работает только один допустимый poller или корректный webhook. Проверены оставшийся webhook, повторная доставка, некорректный secret header и доступ через обязательный proxy/TLS.
- На выбранном бесплатном сервисе проверены простой более 15 минут, холодный старт, повторный запуск/пересоздание экземпляра, доступность БД, сохранность файлов, доставка и ограничения тарифа. Не использовать синтетический keepalive как доказательство 24/7.
- Восстановление backup в отдельную БД сверяет профили, назначения, attempts, answers, документы и ссылки на файлы. Логи и backup защищены и не содержат лишних секретов.

## Gates по фазам

| Фаза | Необходимые доказательства |
|---|---|
| 0 | Подтверждённый отзыв ключа владельцем, baseline/checksums, перечень отсутствующих источников, сохранность legacy |
| 1 | Согласованные D-решения для следующей фазы, просмотренные мобильные/desktop wireframes, схема данных/контента/экзамена, traced backlog |
| 2 | API auth/object permissions, PostgreSQL migrations, restart/restore, PWA/cache/privacy, test Telegram связь; нет реальных секретов в Git |
| 3 | Принятый Balance, лицензированные схемы, реальная демонстрация/упражнение, сохранение, назначение инструктором, взрослый пилот 3–5 человек |
| 4 | Отдельная приёмка E/S/T и safety-библиотеки по локалям; детский доступ только после D-04 |
| 5 | Опубликованные policies, полный экзамен/critical/recovery, практика, документ/отзыв; live test интеграций |
| 6 | Полные Studio/editor workflow, scope/права всех ролей, расширенный пилот и аудит публикаций |
| 7 | Фактические показатели квот/нагрузки, измеренные цели и план работы с ограничениями |

Для пилота критические и высокие дефекты сохранения, доступа и безопасности должны быть закрыты; остальные известные ограничения записаны и не мешают согласованному маршруту. Скриншот интерфейса или список закрытых задач сами по себе gate не закрывают.

## Выполнено до этого проектного этапа

В аудите legacy: `pip check`, структурная проверка всех 121 записей/локалей, read-only сверка GitHub HEAD, проверка истории на известные token patterns/private key markers без значений, 41 диагностическая запись проверок, 140 комбинаций guide/scenario callbacks на четырёх языках, полный проход 121 правильного ответа через реальный Dispatcher с локальной API session, границы баллов и имитация ошибки Sheets. Эти проверки обнаруживают дефекты, а не доказывают готовность платформы. Они не являются тестами ещё не написанного backend/PWA и не доказывают работоспособность реального Telegram/Sheets.

В данном этапе подготавливаются только документы, проверка ссылок/комплектности/архива и сохранности исходного checkout. Ни новые API, ни база, ни frontend не реализованы и не запускались. Человеческая методическая проверка всех заданий и новые визуальные прототипы ещё не выполнены.
