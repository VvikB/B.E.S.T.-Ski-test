# B.E.S.T. Academy — реестр решений v2

Статус комплекта: **proposed — на утверждение**. Подготовка документа не равна принятию решения и не разрешает массовый рефакторинг. Дата: 05.11.2026, Москва. Основание: новое ТЗ и [аудит](../../BEST_TECHNICAL_AUDIT_RU.md). Полное проектное ZIP-досье отсутствует.

Уже заданные ограничения: продолжать существующий продукт; сохранять код/учебные данные и историю решений; не заменять полный банк демонстрацией; не публиковать секреты/опасные инструкции; нулевые обязательные расходы на хостинг; единые серверные правила; отдельная методическая приёмка. Это требования, а не вопросы для повторного согласования.

| D-06 | Все обязательные задания нужны для экзаменационного допуска; critical не обходится досрочной сдачей; практика отдельна | Список/критерии critical, продолжение после ошибки, правила практики и полномочия экзаменатора | Экзамен и итоговый статус |

| D-09 | Разные документы обучения/теории/практики, номер/проверка/отзыв; внутренний итог только по полным основаниям | Названия и права на документ, требования практики, минимум публичных полей | Выдача и verification |
| D-10 | Сначала испытать конкретную бесплатную площадку; webhook при подтверждённом wake/HTTPS либо polling при допустимом worker | Точный URL Netrun/тарифа, условия аккаунтов, допустимые ограничения доступности | Развёртывание, обещания режима работы |
| D-11 | Импортировать всё в draft с occurrence ID; полный дубль не удалять автоматически, историю версий сохранить | Участь дубля и неполных кейсов, правила сравнения/переиздания | Публикуемый blueprint и content migration sign-off |
| D-12 | Backup вне экземпляра, encrypted, ежедневный и перед миграцией; restore обязателен | Хранилище, ответственный, retention, достижимые RPO/RTO на бесплатных условиях | Пилот с реальными данными |
| D-13 | Светлая альпийская система, кириллица, умеренная анимация; сначала шесть wireframes и визуальные прототипы | Визуальное направление, права на графику, детская/взрослая подача | Production UI/медиа |

Форма фиксации решения: ID, accepted/rejected/superseded, выбранный вариант, обоснование, автор утверждения, дата, затронутые версии документов и условия пересмотра. Пока все D-01…D-14 имеют статус proposed. Молчание не означает утверждение.

| Медиа/права | Реальные файлы по 40 ссылкам отсутствуют | Предоставить оригиналы/лицензии либо создать по утверждённому списку |

## Инструкция владельцу по ключу Google — P0

1. Открыть Google Cloud Console под уполномоченным аккаунтом, выбрать нужный проект → IAM & Admin → Service Accounts → соответствующий сервисный аккаунт → Keys. Сверять учётную запись/ключ в своей консоли, не присылать приватный JSON или значения в чат.
2. Отключить/удалить скомпрометированный ключ через доступные действия консоли. Не удалять весь проект или сервисный аккаунт вслепую. Если конкретный ключ уже отозван, зафиксировать факт; наличие файла в Git не доказывает действительность ключа сейчас.
3. Проверить доступы аккаунта к Google Sheets/Drive и проектные роли, убрать лишние. Проверить доступные журналы/аномалии с учётом того, какие логи действительно включены. Отсутствие записи в неполном журнале не доказывает отсутствие использования.
4. Если интеграция нужна, создать новую разрешённую credential-конфигурацию с минимальными правами; хранить через защищённые настройки среды/хостинга. Не помещать новый JSON в Git, архив отчёта, frontend и логи. Сначала отдельная тестовая таблица.
5. Согласовать удаление старого секрета из текущего дерева и истории, действия для форков/клонов и резервных копий. Это отдельная операция с координацией; один `.gitignore` не исправляет компрометацию. Ротация должна быть выполнена даже при последующей очистке истории.
6. Проверить фактическую работу нового разрешённого доступа и отказ старого, не выводя значения. Сообщить результат, а не пересылать ключ. В текущем этапе эти действия владельца не выполнялись агентом.

## Как согласовать без неопределённого «всё одобрено»

Для начала реализации нужны принятые D-01/D-02, достаточная часть D-03/D-08/D-12 и подтверждённый P0. D-05/D-06/D-09 можно разрабатывать как проект, но запрещено выдавать уровни до утверждения. D-04 не требуется для взрослого пилота, но требуется до подключения детей. D-14 необязателен для независимых функций. Это позволяет двигаться по проверяемым срезам, не принимать спорные правила за автора.
